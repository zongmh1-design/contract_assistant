# 重要设计决定

## D-001：采用单体分层应用

- 问题：第一版如何组织完整流程，同时保持容易理解和替换外部能力？
- 方案：微服务；复杂工作流框架；单体分层应用。
- 决定：使用单体分层应用，服务层顺序编排流程。
- 原因：第一版流程规模有限，单体已能满足事务、测试和演示；调用链更容易学习和排错。
- 缺点：长耗时解析会占用进程；未来出现大量并发任务时可能需要后台任务机制。

## D-002：审批系统通过 Gateway 隔离，第一版使用 Mock

- 问题：开发阶段没有真实企业审批系统。
- 方案：业务代码直接读取样例；先写死某平台 SDK；定义稳定端口并提供 Mock。
- 决定：定义 `ApprovalGateway` 业务端口，第一版提供 Mock 实现。
- 原因：可以真实验证本系统流程，又不会伪装已完成企业平台接入；未来替换适配器即可。
- 缺点：Mock 无法覆盖真实鉴权、限流、网络和平台幂等问题。

## D-003：关键失败进入 blocked，而不是增加 failed 终态

- 问题：附件、解析、规则或外部接口失败后如何继续？
- 方案：直接结束为 `failed`；自动无限重试；进入可人工处理的 `blocked`。
- 决定：关键失败统一进入 `blocked`，记录失败步骤、原因和重试目标。
- 原因：合同审批需要人工可见、可诊断、可恢复；避免静默丢单和无限重试放大故障。
- 缺点：需要管理员查看和触发重试；后续若加入有限自动重试，仍需单独设计次数和退避规则。

## D-004：任务状态集中管理

- 问题：状态由多个服务直接赋值会产生非法跳转和难以追踪的问题。
- 方案：各处直接修改；集中状态转换入口。
- 决定：使用一个简单的状态转换模块维护允许路径和前置条件。
- 原因：能明确回答“当前状态、触发条件、下一状态”，也便于集中测试。
- 缺点：状态前置条件增加时，该模块需要谨慎维护；暂不引入通用状态机库。

## D-005：确定性规则优先，LLM 只辅助复杂语义

- 问题：合同风险既有明确数值/缺失判断，也有复杂语义判断。
- 方案：全部代码规则；全文直接交给 LLM；二者分工。
- 决定：金额缺失、主体缺失、比例、周期和条款存在性等优先用确定性规则；复杂语义后续再引入结构化 LLM 辅助。
- 原因：确定性规则可复现、易测试；LLM 结果必须附带证据并受结构校验，不能直接产出不可解释结论。
- 缺点：规则维护有成本；LLM 辅助部分仍存在不稳定性。本阶段不实现二者。

## D-006：保留值、证据、位置和提取状态

- 问题：只保存最终字段值无法判断提取来源和可靠性。
- 方案：仅保存值；保存值及证据元数据。
- 决定：每个重要字段保留 `value`、`source_text`、`position`、`extract_status`。
- 原因：法务可以复核，规则命中可以追溯，失败与不确定结果不会被误认为空值。
- 缺点：数据体积更大，JSON 结构需要版本控制。

## D-007：SQLite 起步，仓储隔离持久化

- 问题：培训项目需要持久化、去重和事务，但不希望先运维数据库服务。
- 方案：JSON/内存；SQLite；直接上 MySQL/PostgreSQL。
- 决定：第一版使用 SQLite 和 SQLAlchemy 2.x，并通过 Repository 隔离数据访问。
- 原因：零运维且能验证唯一约束、关系和事务；未来更换数据库时业务服务不直接改 SQL。
- 缺点：不适合高并发写入和多实例部署；本阶段直接从模型建表，正式保留数据前仍需引入迁移机制。

## D-008：顺序执行，暂不加入队列和工作流框架

- 问题：完整流程有多个步骤和失败恢复，是否立即引入 Celery、Redis 或工作流引擎？
- 方案：引入后台编排基础设施；进程内顺序调用并保存检查点。
- 决定：第一版采用顺序调用和数据库检查点。
- 原因：当前没有并发量、跨进程调度或长任务吞吐的明确需求，额外基础设施会遮蔽核心业务。
- 缺点：单次请求可能较长；真实解析性能和并发需求明确后再评估后台任务。

## D-009：按明确标记和文件名优先级识别主合同

- 问题：一个审批可能同时包含主合同和普通附件，不能随机选择或全部拼接。
- 方案：全部拼接；固定取第一个；按明确标记和文件名优先级识别。
- 决定：先取第一个 `is_main_contract=true` 附件；没有标记时按原顺序匹配“合同、协议、contract、agreement”，英文忽略大小写；仍未识别则阻塞。
- 原因：优先尊重审批系统明确语义，同时为缺少标记的数据提供可解释的确定性回退。
- 缺点：文件名不含关键词且未标记时需要人工处理；第一版不使用内容识别来猜测主合同。

## D-010：完成态要求评论回写成功

- 问题：结果已保存但评论回写失败时，任务能否标记 `done`？
- 方案：结果保存即完成；回写成功才完成。
- 决定：主流程包含评论回写，因此 `done` 要求审查结果已保存且 `write_status=success`。
- 原因：与完整闭环验收一致，避免“内部成功、外部不可见”被误报为完成。
- 缺点：审批平台短暂不可用会让已完成审查的任务保持 `blocked`；重试时只重走回写检查点。

## D-011：instance_id 是主业务标识，approval_code 同时唯一

- 问题：重复拉取应该依据哪个字段识别同一审批，并如何防止标识冲突？
- 方案：仅用 Python 查询判断；只约束 `instance_id`；分别约束两个外部标识。
- 决定：以审批平台稳定的 `instance_id` 作为主业务标识；数据库同时对 `instance_id` 和 `approval_code` 建立单列唯一约束。
- 原因：`instance_id` 用于稳定关联外部实例，`approval_code` 的唯一约束可以阻止异常数据用新实例 ID 重复创建同一审批。同步时只有两个标识指向同一记录才允许更新可变字段。
- 缺点：如果未来某审批平台允许复用审批编号，需要调整 `approval_code` 约束，并改成“平台标识 + 编号”的组合唯一约束。

## D-012：以 SHA-256 判定附件复用或更新

- 问题：重复准备同一个外部附件时，如何避免重复文件，又能发现上游内容变化？
- 方案：只看附件 ID；每次都保存新文件；下载后比较 SHA-256。
- 决定：数据库以 `task_id + external_attachment_id` 唯一；每次重新获取 Mock 内容并计算 SHA-256。哈希一致且本地文件存在时复用，哈希变化时覆盖目标文件并更新同一记录。
- 原因：附件 ID 负责定位同一逻辑附件，SHA-256 负责确认实际内容是否相同，逻辑简单且可测试。
- 缺点：为了比较哈希仍需重新获取附件字节；第一版不保存旧文件和复杂版本历史。

## D-013：阶段 3 文档读取结果暂不落库（已由 D-016 演进）

- 问题：文档读取阶段是否需要提前创建 `ContractParse`？
- 方案：立即创建解析表；把结果写临时 JSON；使用 Pydantic 值对象返回。
- 决定：本阶段使用 `DocumentReadResult` 作为 Pydantic 值对象，通过 API 返回，并用 `TaskLog` 记录成功或失败；不创建 `ContractParse`。
- 原因：当前只验证读取器边界，还没有字段和条款提取结果。提前建解析表会混合两个阶段的职责。
- 缺点：读取结果不会跨请求查询或复用；进入字段提取阶段前需要单独设计持久化边界。

## D-014：需要 OCR 的文档进入 blocked

- 问题：扫描 PDF 和图片没有可用文本时，是继续保持 `parsing` 还是进入 `blocked`？
- 方案：返回空文本并视为成功；保持 `parsing` 等待未来步骤；明确阻塞。
- 决定：返回 `requires_ocr=true`、`read_status=ocr_required`、`error_code=OCR_REQUIRED`，并将任务阻塞在 `document_reading`。
- 原因：本阶段以取得有效文本才算成功；继续运行会把空文本误传给后续处理。文本有效性采用至少 10 个字母数字字符的简单阈值，只排除空白、纯标点和明显过短内容。
- 缺点：很短但真实有效的文档可能被判为需要 OCR 或内容为空；后续可根据真实样本调整阈值。

## D-015：retry 暂时仍从附件准备恢复

- 问题：随着失败点增加，单一 retry 入口如何恢复？
- 方案：立即建设复杂恢复引擎；本阶段保留现有行为并记录债务。
- 决定：当前 retry 仍执行 `blocked -> parsing -> 重新准备附件`，不实现按阶段分派。
- 原因：现阶段只有附件和读取两个小闭环，先保持调用链简单。
- 缺点：未来 `attachment`、`document_reading`、`field_extraction`、`reviewing`、`comment_writeback` 都可能阻塞；必须根据 `blocked_stage` 从正确检查点恢复，不能长期重复准备附件。

## D-016：原始读取快照与 ContractParse 分开持久化

- 问题：后续 OCR、字段提取和审查需要跨请求消费原始文本，但 `ContractParse` 的职责是字段与条款等业务解析结果。
- 方案：每次重新读取文件；把原始文本塞入 `ContractParse`；新增附件级读取快照。
- 决定：新增 `DocumentReadSnapshot`，通过外键关联 `ApprovalAttachment`，保存原始文本、blocks、读取状态、文件 SHA-256 和 Reader 版本；不冗余保存 `task_id`。
- 原因：文件读取事实可以独立复用和审计，不会与字段/条款提取状态混合；任务查询可通过附件关系完成。`blocks` 第一版存 JSON，因为当前没有单块 SQL 查询需求。
- 缺点：原始全文会增加数据库体积；目前没有迁移脚本、压缩、全文搜索或大文档分片策略。

## D-017：成功读取按 SHA-256 与 Reader 版本复用

- 问题：重复调用读取接口时如何避免无意义解析，又能在文件或 Reader 变化后得到新结果？
- 方案：每次读取；只按附件 ID 复用；按附件文件版本和 Reader 版本复用。
- 决定：仅当 `attachment_id + attachment.sha256 + reader_version` 匹配已有 `success` 快照时复用并写 `DOCUMENT_READ_REUSED`；SHA-256 或 Reader 版本变化时新增快照，不删除历史记录。
- 原因：相同字节和相同读取逻辑的成功结果具有稳定复用条件；失败及 `ocr_required` 不伪装成成功缓存。
- 缺点：当前用查询实现复用，没有为并发重复请求增加数据库唯一约束；如果以后并发执行读取任务，需要补充抢占或幂等约束。

## D-018：有附件归属的读取失败也保存快照

- 问题：失败结果是否持久化，尤其是文件缺失、损坏或需要 OCR？
- 方案：只存成功；只写 TaskLog；保存所有可归属到附件版本的读取尝试。
- 决定：只要存在附件和 SHA-256，就保存失败或 `ocr_required` 快照；完全没有主附件或缺少可靠 SHA-256 时只记录日志并阻塞，因为无法形成可信的附件版本快照。
- 原因：后续可查询某个附件版本为何未取得文本，同时不制造无法可靠关联版本的数据。
- 缺点：同一失败条件反复执行会保留多条失败快照；复杂失败去重留待真实运行需求出现后处理。

## D-019：OCR Provider 通过 OcrEngine 隔离

- 问题：业务流程需要真实 OCR，但不应绑定某个模型库或云 API。
- 方案：Service 直接调用 RapidOCR；同时接入多个 Provider；定义一个单图识别端口并提供一真一 Mock。
- 决定：`DocumentOcrService` 只依赖 `OcrEngine`；第一版真实实现为 RapidOCR + ONNX Runtime CPU，测试使用 `MockOcrEngine`。
- 原因：当前 Windows 11、Python 3.12 环境已实际验证 CPU 推理，默认模型支持中英文，不依赖 Tesseract、CUDA 或付费服务；Mock 可稳定模拟多页、空结果和异常。
- 缺点：本地模型增加安装体积和首次初始化时间；真实识别质量仍需用企业合同扫描件验收。

## D-020：扫描 PDF 使用 PyMuPDF 临时逐页渲染

- 问题：pypdf 能提取文字层，但不能把扫描 PDF 页面稳定转换为 OCR 图片。
- 方案：调用系统 Poppler；替换现有 PDF Reader；OCR 路径单独使用 PyMuPDF。
- 决定：保留 `PdfDocumentReader + pypdf` 处理文本型 PDF，仅在 `ocr_required` 路径用 `PyMuPdfPageRenderer` 以 200 DPI 逐页渲染临时 PNG。
- 原因：职责清楚，真实页码可传入 OCR blocks；临时目录自动清理，不污染合同存储。
- 缺点：PyMuPDF 是新增二进制依赖；同步逐页 OCR 对大合同耗时较长，本阶段不引入队列或并行。

## D-021：OCR 继续生成 DocumentReadSnapshot

- 问题：OCR 文本是否需要另一套表或覆盖原 `ocr_required` 快照？
- 方案：覆盖旧快照；新增 OCR 专用表；新增同结构读取快照。
- 决定：OCR 成功或失败都新增 `read_method=ocr` 快照，不覆盖源读取记录。成功复用条件为附件 SHA-256、OCR Provider 版本和成功 OCR 快照同时匹配。
- 原因：后续提取阶段只消费统一成功快照；源判断、OCR 尝试和历史版本均可审计。
- 缺点：同一附件会保留多条快照，后续消费方需要明确选择当前文件版本的最新成功结果。

## D-022：OCR 使用专用恢复入口，不扩建通用重试引擎

- 问题：`ocr_required` 已把任务阻塞，但通用 retry 仍会重新准备附件。
- 方案：立即重写全部 retry；OCR 前保持 blocked；增加局部恢复方法。
- 决定：`POST /api/tasks/{task_id}/ocr` 校验前置快照后，通过 `TaskStateService.resume_for_ocr` 执行 `blocked(document_reading) -> parsing`，直接复用现有附件；OCR 失败再次阻塞于 `document_reading`。
- 原因：首次验证了按失败阶段恢复且没有重复下载，同时控制了本阶段范围。
- 缺点：其他失败阶段仍未获得精确恢复能力；通用 retry 设计债务继续保留。

## D-023：统一选择当前有效 DocumentReadSnapshot

- 问题：字段提取、未来规则和 LLM 都需要同一份当前原文，不能各自实现快照查询。
- 方案：调用方自行查询；在 Repository 暴露零散条件；建立 `DocumentSourceSelector`。
- 决定：选择器只返回当前主附件、当前附件 SHA-256 下 ID 最新的 `success` 快照。
- 原因：文件更新后不会误用旧文本；OCR 与普通 Reader 对后续消费者透明；选择规则只有一个维护点。
- 缺点：目前“最新”使用数据库 ID 顺序；未来若加入人工指定有效版本，需要扩展明确的激活机制。

## D-024：ContractParse 直接关联读取快照

- 问题：结构化事实如何准确追溯到原始文本版本？
- 方案：只关联任务；关联任务和附件；直接关联 `DocumentReadSnapshot`。
- 决定：`ContractParse.document_read_snapshot_id` 是唯一来源外键，不冗余保存 `task_id/attachment_id`；一个快照允许多个解析历史。
- 原因：字段证据、文件 SHA、读取方式和 Extractor 版本可以完整追踪，避免重复归属字段不一致。
- 缺点：按任务查询需要连接快照和附件表；培训项目当前数据量下可接受。

## D-025：字段缺失不是系统失败

- 问题：合同天然可能没有编号或某类条款，是否应当让任务 blocked？
- 方案：缺失即异常；所有缺失都算成功；区分事实状态与程序状态。
- 决定：字段使用 `found/not_found/ambiguous/failed`；全部目标 found 时 `ContractParse=success`，Extractor 正常完成但存在非 found 字段时为 `partial`，程序异常才为 `failed` 并 blocked。
- 原因：缺失本身也是可供后续规则使用的事实，不能与代码崩溃混淆。
- 缺点：后续规则必须显式理解 `not_found` 和 `ambiguous`，不能只读取 value。

## D-026：确定性 Extractor 先建立可解释基线

- 问题：第一版字段和条款提取应使用复杂 NLP、LLM 还是简单确定性方法？
- 方案：立即调用 LLM；构建复杂 NLP；使用正则、字段标签、条款标题和 block 顺序。
- 决定：实现 `ContractExtractor` 统一端口及 `DeterministicContractExtractor`；合同编号、金额、币种、日期和双方采用明确规则，条款按标题延伸到下一标题。
- 原因：结果稳定、容易测试，每个结果都能记录 `extract_method` 和原始 block 位置；未来 LLM 可输出同一 Schema。
- 缺点：对自由表达、表格复杂布局、同义词和无标题条款覆盖有限；本阶段不宣称通用合同理解。

## D-027：ContractParse 按快照和 Extractor 版本复用

- 问题：重复调用结构化提取接口是否需要再次运行 Extractor？
- 方案：每次提取；只按任务复用；按明确输入和算法版本复用。
- 决定：`document_read_snapshot_id + extractor_name + extractor_version` 相同，且状态为 `success/partial` 时复用并记录 `CONTRACT_PARSE_REUSED`；输入快照或版本变化时新增记录，旧历史保留。
- 原因：相同输入与算法的可用结果无需重复计算，同时允许算法升级重新生成事实。
- 缺点：当前没有并发抢占或数据库唯一约束，并发重复请求仍可能产生重复记录。

## D-028：规则定义与确定性执行代码分开

- 问题：风险等级、阈值和建议如果写入 `if/else`，规则调整必须改代码且难以解释。
- 方案：全部硬编码；立即建设通用规则 DSL；`ReviewRule` 保存定义，Engine 支持少量明确模式。
- 决定：`ReviewRule` 保存风险等级、建议、版本及 JSON 格式 `match_text`；`DeterministicRuleEngine` 只实现 `field_missing/numeric_threshold/keyword/presence`，`future_llm` 跳过。
- 原因：可配置内容与执行职责清楚，同时避免为第一批九条规则建设复杂 DSL 或插件系统。
- 缺点：`match_text` 当前依赖约定的 JSON 结构，没有独立配置 Schema 或管理接口；修改时需要同步升级 `rule_version`。

## D-029：确定性规则优先于 LLM

- 问题：字段缺失、明确比例和关键词是否应交给 LLM 判断？
- 方案：全部使用 LLM；确定性与 LLM 混合；先执行可解释的确定性规则。
- 决定：本阶段只对已结构化事实执行确定性判断，复杂公平性、合规性和隐性风险暂不实现。
- 原因：相同输入得到稳定结果，阈值和证据可复核，成本低且方便单元测试；不会用“假智能”制造无法解释的风险。
- 缺点：自由表达、中文数字和隐含语义覆盖有限，后续仍可能需要 LLM 辅助，但必须沿用证据结构。

## D-030：RuleHit 保存证据类型、位置和阈值上下文

- 问题：缺失规则没有原文证据，数值规则又包含派生判断，单个 `evidence_text` 无法区分。
- 方案：只保存命中布尔值；重新搜索全文；保存 ContractParse 证据及类型、实际值和期望值。
- 决定：RuleHit 保存 `evidence_text/evidence_position/evidence_type/actual_value/expected_value/hit_message`。原文位置直接复制 ContractParse，缺失说明标记为 `missing`，阈值判断标记为 `derived`。
- 原因：命中能够回答“依据哪里、实际多少、要求多少”，并避免二次全文搜索猜位置。
- 缺点：缺失类 `evidence_text` 是系统说明而非合同原文，消费方必须展示 `evidence_type`。

## D-031：按 ContractParse、规则和规则版本复用命中

- 问题：重复执行规则会产生重复 RuleHit，但规则条件升级后又必须保留新旧历史。
- 方案：每次删除重建；只按 parse + rule 去重；按 parse + rule + version 唯一。
- 决定：数据库建立 `(contract_parse_id, rule_id, rule_version)` 唯一约束；相同版本已有命中直接复用，版本变化新增命中，不删除旧记录。未命中不落库。
- 原因：数据库层保证重复命中的幂等性，并允许审计规则版本变化。
- 缺点：没有单独的审查运行表，无法持久化每次执行的未命中集合；本阶段通过 TaskLog 记录运行概况。

## D-032：风险汇总暂不创建 ReviewResult

- 问题：规则阶段是否应提前保存最终审查结果？
- 方案：立即创建 ReviewResult；只保存 RuleHit 并即时汇总。
- 决定：返回临时 `RuleReviewSummary`；存在 high 则 high，否则存在 medium 则 medium，否则 low。任务成功后保持 reviewing。
- 原因：评论回写和最终结果版本尚未实现，提前持久化会混合阶段职责。
- 缺点：汇总不能独立跨请求查询；下一阶段若实现 ReviewResult，需要明确其版本和命中集合。
